# Why Tally & Trace Felt Slow, and What We Did About It

[Tally & Trace](/work/tallyandtrace) got slow. Not broken, just slow. Opening a page took long enough to notice. Saving a transaction froze the screen for a moment. On a finance app you open ten times a day, that adds up.

This post covers why it was slow, what we changed, and what the numbers look like now.

A note on the numbers. Every figure below was measured on a synthetic test dataset, not on anyone's real accounts. The app runs on a free-tier instance with roughly 0.1 CPU, so "10% CPU" in the timings means we throttled the benchmark to match. Treat the figures as before and after on one fixture, not as promises.

## Why it was slow

There was no single cause. There were seven small ones, and they stacked.

**One endpoint served every screen.** The app had a single dashboard snapshot endpoint. Every page asked it for everything. Over time the number of SQL statements behind it grew from about 20 to 530.

**No per-request context.** Each piece of code that needed the event projection computed it again. It ran 4 times per request. Access checks ran about 18 times. Nothing was shared across the request.

**Eager loading of sharing relationships.** The sharing relationships were set to load eagerly (SQLAlchemy `selectin`). That quietly added about 186 statements to the snapshot.

**Credit-card statements replayed history.** Each read rebuilt card statements from the start of history. So the cost grew every month the user kept using the app.

**It was CPU-bound, in Python.** Most of the time was not the database. It was Python burning CPU on a 0.1-CPU instance. Fewer statements and less repeated work meant less CPU.

**Saves froze the page.** Cache invalidation used broad tags, so one save refetched a lot. A blocking "busy" overlay then covered the screen while it did.

**No performance budgets.** Nothing failed when the snapshot got heavier. So it kept getting heavier, one reasonable change at a time.

## The fixes, in order

### 1. Measure first: a fixture, a benchmark, and budgets in CI

Before changing behaviour, we built a realistic test fixture and a benchmark script. The script counts SQL statements and response bytes per endpoint. CI now enforces a budget on both. If a change makes the snapshot issue more statements or send more bytes than the budget allows, the build fails.

This came first on purpose. Every later fix is measured against it.

### 2. A single-pass statement engine

The statement engine that builds card statements now walks the transactions once, instead of making repeated passes. Same output, less work.

### 3. Access computed once, sharing relationships set to raise

Account access is now computed once per request and passed around as plain data. The sharing relationships are set to raise an error if anything lazy-loads them. That turns a silent performance bug into a loud one.

The snapshot went from 610 to 336 statements.

### 4. Idempotency keys on creates

This one is about safety, not speed. The next fix retries failed saves in the background, and retries must not create duplicates. Create requests now carry an idempotency key. If the server sees the same key twice, it returns the first result instead of creating a second record.

### 5. Background saves

Saving no longer blocks the page. Changes go into an outbox and sync in the background. The UI shows stacked toasts and a "Saving…" row for pending items. Failed saves can be retried, and finished ones can be undone. The blocking overlay is gone.

### 6. Stored closed credit-card statements

A closed card statement never changes unless someone edits a transaction inside it or changes the card's billing settings. So we stopped recomputing it. Closed statements are now stored, and kept current by write-through: when a transaction or a card's billing settings change, the affected statements are rebuilt in the same transaction. A per-card advisory lock serialises those writers.

Readers take a short shared lock, scoped to a savepoint. That keeps a read consistent with in-flight writes without deadlocking against them.

The result is that the snapshot no longer grows with history. One year of data and four years of data take the same number of statements.

### 7. A data version, ETag, and 304 Not Modified

The database now keeps a data version. A deferred statement-level trigger bumps it once per writing transaction, however many rows that transaction touched. The API turns it into an ETag. If the client already has the current version, the server answers `304 Not Modified` and skips the work.

A repeat page open at 10% CPU went from about 12.0 s to 2.0 s. In the benchmark, 10 of 10 eligible requests came back as 304.

### 8. One request context per request

Now each request builds one context object. The event projection runs once, and access is looked up once. Everything else reads from it.

The snapshot went from 344 to about 61 statements, and CPU time from 217 to 92 ms. Opening the transactions page at 10% CPU went from 7.9 s to 4.4 s.

### 9. A lean endpoint for the Due card

The Due card only needs a few fields, but it fetched them with 4 separate requests. It now has its own `/dashboard/due` endpoint, which answers in one. For the main test user, statements dropped from 93 to 59, and the payload from 224 KB to 158 KB.

### 10. The Due card on the new endpoint

The card now calls the lean endpoint and refreshes on its own cache tag, so a save only refetches what it actually changed. Opening the Transactions page went from 11 requests to 8, and the card's own share went from 7 to 3. After saving a transaction, the follow-up requests went from 9 to 4.

We aimed for 6 on page open and stopped at 8. Each request that's left draws something on the first screen: account and category names, schedule labels, or tab badges. Deferring them would make labels pop in after the page appears, which is worse than one more request. An older server that doesn't have the endpoint still works: the card falls back to the old queries.

## Lessons

**Put budgets in CI.** The snapshot went from 20 statements to 530 without any one change looking wrong. A budget that fails the build would have caught it at 40. We have that now.

**Measure before you fix.** The benchmark came before the first fix. It showed that most of the time was CPU, not the database, which changed what we worked on.

**Protect behaviour with golden-file tests.** Several of these changes rewrote how balances and statements are computed. Golden-file tests pinned the exact output before the rewrite, and the output had to match afterward. In a money app, "faster" is only useful if the numbers stay the same.

**Know the trade-offs you accepted.** Stored statements and write-through add write-path complexity and locks. We chose that over recomputing history on every read. The data version also invalidates on any write, not just writes that matter to a given page. That is coarser than ideal, and it is simple and safe. We would rather be correct and slightly conservative than fast and occasionally stale.
